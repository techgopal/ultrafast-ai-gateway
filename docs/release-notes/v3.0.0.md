# Ultrafast 3.0.0

Ultrafast gets a short name. The command, the image, the release archives and the client
packages are now `ufaigw`, after [ufaigw.com](https://ufaigw.com), the way Kubernetes is
typed `kubectl`. "Ultrafast" stays the product's name. Nothing about how the gateway
behaves changes, and there is no database migration.

## The names

| | 2.x | 3.0.0 |
| --- | --- | --- |
| Command | `ultrafast` | `ufaigw` |
| Archives | `ultrafast-v2.1.1-<target>.tar.gz` | `ufaigw-v3.0.0-<target>.tar.gz` |
| Image | `ghcr.io/techgopal/ultrafast-ai-gateway` | `ghcr.io/techgopal/ufaigw` |
| Image data directory | `/var/lib/ultrafast` | `/var/lib/ufaigw` |
| Crates | `ultrafast-translate`, `ultrafast-client` | `ufaigw-translate`, `ufaigw-client` |
| PyPI | `ultrafast`, `ultrafast-admin` | `ufaigw`, `ufaigw-admin` (`import ufaigw`, `import ufaigw_admin`) |
| npm | `@ultrafast/client`, `@ultrafast/admin` | `@ufaigw/client`, `@ufaigw/admin` |
| Default OTel service name | `ultrafast` | `ufaigw` |

Unchanged: the `UF_*` settings, the config file format (`ultrafast-config`, so a 2.x
export imports), the MCP `_meta.ultrafast` key, and the repository.

## Upgrading

- **Binary.** Download the `ufaigw` archive and replace `ultrafast` with `ufaigw` in your
  scripts and service files (`ExecStart`). The data directory and its files stay as they
  are. There is no `ultrafast` alias.
- **Docker.** Use `ghcr.io/techgopal/ufaigw:3.0.0` and mount your existing volume at
  `/var/lib/ufaigw`, for example `-v ultrafast-data:/var/lib/ufaigw`. The data is the same;
  only the mount point moves. The image's user keeps uid and gid 999, so the volume needs
  no `chown`. A volume left at `/var/lib/ultrafast` makes the gateway refuse to start and
  say where to mount it, instead of starting empty.
- **OpenTelemetry.** Set `UF_OTEL_SERVICE_NAME=ultrafast` to keep existing dashboards.
- **Webhooks and guardrails** see the User-Agent `ufaigw/3.0.0`, and alert payloads say
  `"gateway": "ufaigw 3.0.0"`.

## Fixed

- A sign-in while another request was writing could fail with "database is locked" (a
  500); it now waits for the write lock.
